BFF Architecture

This is not a normal Laravel CRUD app. Understanding this changes how you assess quality.

Lesson 2 • 7 min read • Prerequisites: Lesson 1
Zone: System architecture, quality implications

The Shocking Truth

This Laravel app has no business data in its database.

No quotes table. No policies table. No Eloquent models for insurance products.

What This App Actually Is

A Backend-for-Frontend (BFF) — a thin layer between Vue.js and a remote insurance API called PAI.

The Request Flow (Memorize This)

Browser (Vue)
  ↓
Laravel Controller
  ↓
app/Services/GlobalBaseService.php  ← HTTP client
  ↓
PAI (remote insurance API)  ← actual system of record
  ↓
Response reshaping
  ↓
Back to Vue

What Laravel Actually Owns

Layer What It Does
Auth & Session Login, permissions, user state
Routing & Middleware Permission checks before hitting PAI
PDF Generation Blade templates → Snappy/MPDF → PDF download
Response Reshaping PAI JSON → Vue-friendly structure

What PAI Owns (The Real Database)

  • All quote data
  • All policy data
  • All endorsement data
  • Commission, reinsurance, clauses
  • Product configuration

Quality Implications for CEO Meeting

1. "Missing Field" Bugs Are Usually PAI Gaps

When a field doesn't display, first suspect: PAI's API response omits it.

Not: missing migration, wrong Eloquent relation, database corruption.

Instead: PAI v2 endpoint changed, nested payload missing, API contract drift.

CEO Translation

"Our app doesn't own the data — we pull it from the insurance API. When a field is missing, the root cause is usually the API contract, not our code."

2. No Local Testing Without PAI

You can't run end-to-end tests without a live PAI environment.

Test Type Feasible?
Unit tests (PHP) ✓ Yes — test logic, not data
Vue component tests ✓ Yes — mock API responses
E2E (quote → policy → PDF) ✗ No — requires PAI UAT environment

3. Verification Happens in UAT, Not Locally

The authoritative smoke test is a real staff member doing a real journey in UAT:

  1. Create quote for product X
  2. Hydrate (fill all required fields)
  3. Print PDF → verify layout
  4. Convert to policy
  5. Print policy PDF
  6. Create endorsement
  7. Print endorsement PDF

If this works, the product is live. If it fails at step 3, you have a blocker.

4. The Config File That Matters

.env file:
API_INSURANCE_SERVICE_URL=https://uat-pai.example.com

This URL determines which PAI environment you're hitting:

  • uat-pai → UAT data (safe to test)
  • prod-pai → Production data (customer records, never touch from dev machine)

Risk: Timeout & Network Failures

Every user action = 1 HTTP call to PAI. If PAI is slow or down:

  • Loading a quote takes 10+ seconds
  • Saving a policy times out
  • Staff see blank screens

Mitigation in code:

// app/Services/GlobalBaseService.php
Http::timeout(60) // 60 seconds before giving up
CEO Risk Summary

We depend on PAI uptime. If PAI goes down, our app becomes read-only (can't save). If PAI is slow, our app is slow. We mitigate with 60s timeouts and error handling, but we can't eliminate this dependency.

Why This Architecture Was Chosen

You don't need to defend this decision (it predates you), but understand the tradeoff:

Alternative Why Not
Replicate PAI data locally Sync complexity, stale data, dual writes
Cache PAI responses Insurance data must be real-time (regulatory)
Build our own system of record PAI already exists, massive duplication
