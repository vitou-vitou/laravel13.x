Verification Checklist

The exact steps your team runs before calling a product "done"

Lesson 3 • 8 min read • Prerequisites: Lesson 2
Zone: Quality assurance, go/no-go decisions

The Core Question

When your dev says "Product X is done", what does "done" mean?

Definition of Done

All 5 checks pass:

  1. PHP tests green — php artisan test
  2. Static analysis clean — composer analyse (only new code checked)
  3. Build succeeds — npm run build (JS/Vue/CSS)
  4. Routing verified — node scripts/verify-burglary-routing.mjs
  5. UAT smoke pass — quote → policy → endorsement, all PDFs render

Check 1: PHP Tests

php artisan test

What it catches:

  • Controller logic broken
  • Service methods throwing exceptions
  • PDF view models missing fields

What it doesn't catch:

  • Vue component bugs
  • PAI API contract changes
  • CSS layout issues

Current state: ~200 tests. Most are unit tests for services and controllers. No E2E coverage (requires PAI mock, too brittle).

Check 2: Static Analysis (Larastan)

composer analyse

What it catches:

  • Type errors (passing string where int expected)
  • Undefined properties, methods
  • Null pointer risks
The Baseline File

phpstan-baseline.neon freezes 4,398 legacy errors from old code (pre-Direct Book).

Your new code is checked separately. If composer analyse fails, it's your code that has the issue, not legacy.

Never regenerate the baseline to hide your own error. Fix it instead.

Check 3: Build (npm run build)

npm run build

When to run: Only if JS, Vue, or CSS changed. Skip otherwise (slow — ~2 minutes).

What it catches:

  • Vue syntax errors
  • Import path typos
  • CSS class conflicts (sometimes)

Production CSS trap: npm run dev looks right, but production breaks. Example:


<div class="grid-cols-1 md:grid-cols-2">



<div class="grid-cols-4">
  <div class="col-span-2">...</div>
</div>

Always test with a local build before pushing.

Check 4: Routing Verification

node scripts/verify-burglary-routing.mjs

What it does: Scans Vue Router config for Direct Book products, ensures all required routes exist:

  • Quote create, edit, view
  • Policy create, edit, view
  • Endorsement create, edit, view

Why it matters: Direct Book products share routing patterns. If 0198-directors-officers is missing a policy edit route, this catches it before UAT does.

Check 5: UAT Smoke (The Real Test)

All automated checks are necessary but not sufficient. The authoritative proof:

Manual Journey in UAT Environment

  1. Quote Level
    • Create new quote for product X
    • Fill all required fields (hydrate)
    • Save successfully
    • Print PDF → verify: correct product name, all sections render, no blank tables
  2. Policy Level
    • Convert quote → policy
    • Edit policy (change a field, save)
    • Print policy PDF → verify layout
  3. Endorsement Level
    • Create endorsement from policy
    • Edit endorsement
    • Print endorsement PDF → verify
Common Blocker: PDF Print Failures

Most "done but not done" cases fail at PDF print:

  • Blade template missing a variable
  • PAI payload doesn't include a nested section
  • Table rendering breaks with long text

PDF is non-negotiable. Customers need printed quotes to sign. If PDF fails, product isn't shippable.

Who Runs What, When

Check Who When
1–4 (automated) Developer before commit Every feature branch
5 (UAT smoke) QA or lead dev Before marking JIRA "Done"
All 5 Team lead (you) Before CEO demo or release

Red Flags to Watch For

Dev Says What It Means Your Response
"It works on my machine" Didn't run npm run build Not done. Run check 3.
"PDF is just formatting" Skipped UAT smoke Not shippable. PDF is customer-facing.
"Tests pass but PAI changed" API contract drift Blocker. Coordinate with PAI team.
"I'll fix it after release" Cutting corners No. Fix before merge.
