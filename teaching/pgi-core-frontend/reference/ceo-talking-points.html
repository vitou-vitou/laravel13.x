4. Technical Risk Profile

Known Risk: PAI Dependency

What it is: Our app pulls data from PAI (insurance API). If PAI is down, we can't save quotes or policies.

Mitigation: 60-second timeout, error handling, monitoring. But we can't eliminate this dependency.

Impact: PAI downtime = our app becomes read-only.

Quality Confidence: High

  • 5-step verification checklist enforced

  • UAT smoke gated for live journeys per 7pj cells

5. If CEO Asks...

"Can customers use this today?"

Yes, for the 11 live journeys. Staff can create quotes, convert to policies, issue endorsements, and print PDFs when that cell is UAT-verified.

"What happens if PAI goes down?"

App becomes read-only — staff can view existing data but can't create new quotes or save changes. We monitor PAI uptime and have escalation paths to their team.

"How do we know the PDFs are correct?"

Manual verification in UAT: we print a sample quote, policy, and endorsement for each product. QA checks layout, field population, and formatting. All 9 live products passed.

"Why aren't the 3 WIP products live yet?"

Code is done, but they haven't passed final UAT smoke test. We don't ship until all 5 checks pass. ETA: [team's estimate].

"What's our test coverage?"

~200 PHP unit tests for controllers and services. Static analysis catches type errors and null pointer risks. But E2E coverage is manual (UAT smoke) because we depend on a live PAI environment.

"Can we add more products?"

Yes. The Direct Book architecture is designed for this. Each new product follows the same pattern: Vue components + Laravel services + PAI integration + PDF templates. Estimated effort: [consult team].
